## 📐 1. 誤差の内訳（前提の共有）

「どこを削ると待機誤差が減るのか」を先に共有しておかないと、最適化の議論が空回りします。
現状の誤差の支配項を大きい順に並べると、以下のようになると**見積もって**います。

> **以下の内訳は未測定の推定です。** 実際の寄与率を確定させるのが後述の案 (1) であり、
> それまでは本節の順序も幅も仮説として扱ってください。

| # | 要因 | 想定オーダー（推定） | 性質 |
|---|---|---|---|
| 1 | **OS のスケジューリング** — プリエンプト、クォンタム（10〜30ms 程度）、コア移動 | 数十 µs 〜 ms | **支配項**。ユーザーモードから消せない |
| 2 | **タイマー分解能** — `WaitableTimer` の起床粒度 | 0.5 〜 1ms | OS 側の粒度。末尾スピンで隠す設計 |
| 3 | **スピンループ 1 反復の粒度** — `qpc_now_us()` 1 回分 | 推定 30 〜 80ns | 実装で削れる |
| 4 | **命令レベルのオーバーヘッド** — 比較・分岐など | ns 未満 | 実装で削れる（が誤差として無視できる） |

### この内訳から導かれる結論

- **アセンブリによる最適化が削れるのは 3 と 4 のみで、支配項である 1 には一切効きません。**
  スピンループを手で書き直しても、プリエンプトされた瞬間に数十 µs〜ms 単位で吹き飛びます。
- **最も効く箇所は既にアセンブリ相当です。** スピン中に発行している `YieldProcessor()` は、
  x86 では `_mm_pause`（`PAUSE` 命令）、ARM64 では `__yield`（`YIELD` 命令）の intrinsic に展開されます。
  つまりホットループの中核は既に「1 命令」まで落ちており、ここに手書きアセンブリを持ち込む余地はありません。
- したがって、3 の領域で意味のある改善余地は「命令の書き方」ではなく **`qpc_now_us()` 内の 64bit 除算**
  という、算術そのもののコスト側にあります（後述の案 (5)）。
- 支配項 1 に対して打てる手は「誤差を減らす」ではなく「**誤差が出たあとの振る舞いを規定する**」方向、
  すなわち周期ループのドリフト補正（案 (2)）です。

#### (2) `usleep_ticker_*` の API 案

```c
// ---- 周期ループ（案・未実装） ----
typedef struct usleep_ticker_t
{
	uint64_t next_us;	// 次の格子点（絶対時刻・steady）
	uint64_t period_us;	// 周期
	int      catchup;	// USLP_CATCHUP_SKIP / USLP_CATCHUP_ACCUMULATE
} usleep_ticker_t;

usleep_ticker_init(&t, period_us, USLP_CATCHUP_SKIP /* or ACCUMULATE */);
uint64_t missed = usleep_ticker_wait(&t);	// 何 tick 落としたかを返す
```

要点は、**遅延したときに「バーストで取り返す」（`ACCUMULATE`）か「落として次の格子に乗る」（`SKIP`）かを
利用者が選べる**ことです。ドリフトを累積させない実装を DLL 側に持てば、利用者ごとに書かれる
「`next += period` とすべきところを `now + period` にしてしまう」類の実装ミスが消えます。
`missed` の戻り値により、利用者はフレームスキップ等の判断ができます。

現行 README の使用例（1ms 周期の締切方式）は、この API のリファレンス実装に相当します。
API 化してもそれらの例が壊れないよう、`usleep_until_steady_us()` は残す前提です。

#### (3) `usleep_calibrate()` の狙い

`usleep_calibration_t`（案）で結果を**取り出し／流し込み**できると、CI と本番で同じ値を再現できます
（測定環境が不安定な CI では、本番で採取した値を注入して固定する運用が取れる）。

解決したい既知の残件は次のものです。[test_result.md](./test_result.md) の実測により、
**1ms 周期・`spin_last_us=200µs` の設定では 2/3 以上の反復で末尾スピンに 1 回も到達していない**
ことが判明しています（タイマーが締切を過ぎてから起床するため）。
※ この `200` は**既定値ではありません**。BALANCED の既定 `spin_last_us` は **250µs** であり、
`200` は BALANCED の内部閾値 `prefer_spin_below` の値であると同時に、当該測定で明示指定された設定値です。
いずれにせよ「固定の既定値では環境と周期に噛み合わない」という構造の問題であり、
環境ごとに実測して決めるのが筋、というのがこの案の動機です。

#### (5) 除算除去の根拠（見積もり）

現状の `qpc_now_us()` はスピン 1 反復ごとに 64bit 除算を伴います。

```c
const uint64_t q      = ticks / f;
const uint64_t r      = ticks % f;
const uint64_t rem_us = (r * 1000000ULL) / f;
```

`ticks / f` と `ticks % f` は x86 の `div` が商と剰余を同時に出すため 1 命令に融合され得ますが、
それでも**最低 2 回**の 64bit 除算が残ります。x86 の 64bit `div` は概ね 20〜40 サイクルのレイテンシで
（マイクロアーキテクチャ依存・**未実測の一般的な目安**）、しかも結果が直後の比較に使われる
**依存チェーン上に乗る**ため、アウトオブオーダー実行では隠しきれません。

QPC 周波数 `f` は起動後不変です（実装も `g_qpc_freq` に `std::atomic` でキャッシュ済み）。
そこで逆数（multiply + shift、libdivide 方式）を `g_qpc_freq` と同じタイミングで一度だけ計算して
キャッシュすれば、ホットパスから除算を消せます。

効果の見積もりは 2 つあり、**後者の方が実利が大きい**と考えています。

- 待機のオーバーシュートが数十 ns 減る … §1 の項目 3 の話であり、支配項ではない
- **スピン中に焼く CPU サイクルが減る** … 末尾スピンが 1 コアを 100% 占有する設計上、
  ここは電力・SMT 兄弟コアへの圧迫に直結する

いずれも**推定**です。案 (1) の計測が入ってから着手すれば、利得を before/after の実測で示せます。

#### (7) TPAUSE / UMWAIT / MWAITX の検討メモ

CPU に「指定した TSC デッドラインまで低電力サブステートで待つ」ことを指示する命令群です。

| ベンダ | 命令 | 導入 | 備考 |
|---|---|---|---|
| Intel | `TPAUSE` / `UMONITOR` + `UMWAIT` | WAITPKG（Tremont / Alder Lake 以降） | TSC のデッドライン指定で C0.1 / C0.2 サブステートに落ちる |
| AMD | `MONITORX` / `MWAITX` | Excavator 以降 | **リング 3 で使用可** |

**利得は精度ではなく、消費電力と SMT 兄弟コアへの圧迫の低減です。** ここを取り違えないこと。

この DLL の最大の弱点は「**末尾スピンが 1 コアを 100% 占有する**」ことであり、
`USLEEP_SPIN_LAST_US_MAX`（10ms）という上限も、`USLP_LOW_POWER` プロファイルの存在も、
すべてそこから来ています。もし低電力待機で同等の起床精度が得られるなら、
**LOW_POWER と STRICT のトレードオフ自体を緩められる**ことになり、影響は設計思想にまで及びます。

注意点（いずれも実測での確認が必要）:

- **`CPUID` による機能検出が必須。** 未対応 CPU で実行すると `#UD` になります。
- OS が `IA32_UMWAIT_CONTROL` で **C0.2 を無効化**したり、**最大待機サイクル数**
  （既定 100,000 TSC cycles ≒ 数十 µs）を制限している可能性があり、実測での確認が要ります。
- その最大待機長がちょうど**末尾スピン領域（数百 µs 以下）と噛み合う**ので、用途としては相性が良い。
- **検出結果のキャッシュは magic static を避けて `std::atomic` にすること。**
  既存の `g_qpc_freq` / `g_hrtimer_probed` と同じパターン（DllMain のローダーロック制約のため）。
- **仮想環境では使えないことが多く、`PAUSE` スピンへのフォールバックが必須。**

ABI 面では、`UsleepYieldPolicy` の**末尾**に `USLP_YIELD_TPAUSE = 4` を追加する形なら既存の値を
変更しないため互換を保てます（公開ヘッダの「enum の追加は必ず末尾」という既存規約どおり）。

### 🚫 見送り推奨

| 案 | 見送りの理由 |
|---|---|
| **`RDTSC` / `RDTSCP` への置き換え** | QPC は現代の Windows では既にユーザーモードで TSC を読んでおり、syscall は発生しません。差は 20〜30ns 程度（**推定**）。置き換えると invariant TSC の判定、コア間の TSC ずれ、VM マイグレーション、周波数保証を自前で背負うことになります。**QPC はまさにそれを隠すために存在する**ので割に合いません |
| **スピンループ本体の手書きアセンブリ** | 既に `pause` + ロード + 比較のみで構成されており、コンパイラ出力に改善余地がほぼありません。§1 のとおり、削れるのは支配項ではない部分だけです |

## 🚦 4. 着手順の推奨

```
(1) 計測  →  (5) 低リスクで確実に小さく効く  →  (7) 大きいが検出とフォールバックの設計が要る
```

1. **(1) 計測** — 何がどれだけ効いているかを先に確定させる。§1 の内訳が推定のままでは、
   以降の優先度づけがすべて勘になる
2. **(5) 除算除去** — 変更範囲が `qpc_now_us()` に閉じており、API も ABI も変わらない。
   (1) の計測基盤があれば before/after を実測で示せる
3. **(7) TPAUSE 系** — 利得は大きいが、`CPUID` 検出・OS 側の制限・仮想環境フォールバックの
   設計が要る。ABI は `UsleepYieldPolicy` の末尾追加で保てる

(2) (4) (6) は上記と独立なので、手が空いたときに差し込めます。
